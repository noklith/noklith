# Opt-in wallet authentication

`apps/api/src/auth/service.ts` implements an **EOA-only** SIWE service. HTTP sign-in is available only when the operator explicitly enables wallet authentication in testnet mode and supplies a canonical HTTPS origin, sign-in URI, chain allowlist and trusted account inspector. The default remains disabled. An external-wallet sign-in against a deployed service has not yet been verified.

The verifier uses pinned **viem 2.57.3** (MIT), recorded with transitive integrity hashes in `apps/api/package-lock.json`. Installation scripts were disabled. Package source was inspected for the SIWE message builder and EOA signature verifier; cryptography is not implemented locally. Primary references: [ERC-4361](https://eips.ethereum.org/EIPS/eip-4361), [viem message creation](https://viem.sh/docs/siwe/utilities/createSiweMessage), and [viem EOA verification](https://viem.sh/docs/utilities/verifyMessage).

## Implemented behavior

- Explicit canonical HTTPS origin, same-origin URI and chain allowlist are required. There are no runtime defaults that silently select a network. Only the two researched candidate testnet IDs can be configured; mainnet IDs fail closed. The tests use synthetic chain metadata and make no RPC requests.
- Server-issued challenges bind a checksum address, chain, origin, URI, fixed statement, version, 256-bit random nonce, request ID, issue time and five-minute expiry. The service accepts only its exact original message; the same message must also reconstruct identically under the current server configuration. Extra lines and changed fields are rejected.
- A 65-byte EIP-191 EOA signature is checked against the challenge address. Compact, contract-wallet and counterfactual signature formats are not supported. An invalid signature does not consume the nonce or call the account inspector.
- A required injected account inspector must return the actual RPC chain ID and account code. Missing data, a chain mismatch and an unavailable RPC fail closed. Non-empty code is explicitly unsupported, including delegated-code accounts. The [RPC adapter](rpc.md) uses explicitly configured chain endpoints with bounded requests. There is no permissive default inspector.
- After verification, a conditional database update consumes the nonce exactly once. Identity lookup/creation and session insertion occur in the same transaction; a failed insert rolls back consumption. Expiry is checked again after signature/account inspection, including at the exact expiry instant.
- Sessions last one hour, bind address/chain/audience, store only a SHA-256 token hash, and can be revoked. Identity normalization is case-insensitive while responses use checksum addresses. Repeated login uses the same identity. Signatures and private keys are not stored.

Migration `002_siwe_auth.sql` is additive. `wallet_identities`, `siwe_challenges` and `siwe_sessions` are separate from synthetic fixture identities and tokens. A wallet token cannot authenticate to the fixture API, and a fixture token cannot authenticate to this service. Linking wallet identities to actual card ownership remains integration work; no existing fixture ledger is silently assigned to a wallet.

## HTTP contract and request limits

- `POST /v1/auth/challenge` accepts `address` and integer `chain_id`; returns `id`, the exact `message` to sign and `expires_at`.
- `POST /v1/auth/verify` accepts `challenge_id`, `message` and a 65-byte hexadecimal `signature`; returns an expiring bearer token and wallet identity.
- `GET /v1/me` authenticates only the session type configured for that application. `POST /v1/auth/logout` with `{}` revokes only that mode's session and returns 204.
- `/v1/config` advertises `wallet_auth_enabled: true` and public origin/URI/chain metadata only when that application has an explicitly constructed verifier. RPC endpoints and credentials are omitted. Top-ups remain disabled and wallet card/history operations return `503 card_integration_unavailable` after authentication.

Migration `003_auth_rate_limits.sql` adds shared, persistent fixed-minute buckets. Challenge requests permit 10 per source IP and 3 per address; verification permits 20 per IP and 5 per challenge. IPv4 clients are counted per address, IPv6 clients per /64, and each IPv6 /48 additionally gets 30 challenges and 60 verifications per minute. A request with a malformed address or challenge ID is refused with 400 before any bucket is touched. Buckets are checked network → client → subject → shared ceiling and stop at the first refusal, so a refused request never counts against the 3000-request shared minute ceiling; one client or network cannot use it up for everyone. Verification limits run before signature work. Per-client buckets are capped at 65536 rows with saturated counters; when that table is full, new clients are limited by the shared ceiling alone instead of being locked out. Deployment-level controls (for example a Cloudflare rate-limiting rule on `/v1/auth/*`) remain the defence against a distributed flood. Buckets store scoped SHA-256 digests rather than raw IPs/addresses. These hashes are not claimed to anonymize small identifier spaces.

Proxy headers are trusted only from the single address or CIDR block in `TRUSTED_PROXY` (on the server: the local Caddy, which sets `X-Forwarded-For` to the client IP it took from Cloudflare's `CF-Connecting-IP`). Without it, rate limits use the socket peer address. Rate checks run before request-schema validation, after JSON parsing within an 8192-byte body limit. Malformed JSON rejected by the parser is outside these route buckets; deployment-level request controls remain necessary.

A PostgreSQL transaction advisory lock serializes bucket allocation, maintenance and the short session-creation commit across workers. Account inspection remains outside that lock. The session commit shares the maintenance lock so expiry cleanup cannot delete a challenge while a new session is being inserted. Rate-window and commit timestamps are read after acquiring the lock. Once per minute, an incoming authentication request removes expired sessions followed by expired challenges that no session references. Expired buckets are removed on each authentication request. Active sessions retain their challenge even after its five-minute sign-in window; revoked sessions remain stored until their expiry. Maintenance is lazy, so an idle deployment retains expired records until the next authentication request. Wallet identities are not automatically deleted.

When wallet authentication is configured, `/ready` also requires the `auth_maintenance` sentinel row created by migration 003. A missing table or row returns 503.

## Verification scope

`test/auth.test.ts` uses freshly generated ephemeral keys only in test memory. It tests real signing and recovery, message substitutions, another signer, malformed signatures, nonce uniqueness, six concurrent verification attempts, time boundaries, RPC/code policy failures, transactional rollback, session isolation, revocation, and reopening a persisted database. No user secret is requested or embedded.

`test/auth-http.test.ts` covers the HTTP contract, real test signatures, token revocation and cross-mode isolation, unavailable wallet card operations, schema rejection, unsupported code-bearing accounts, concurrent rate limits shared by app instances, untrusted proxy headers, global and storage caps, expiration cleanup and readiness. It also checks `/v1/me` over a temporary loopback TCP listener before and after logout. Its account inspector is a test double. `test/auth-rate-limit.test.ts` checks a queued request crossing a minute boundary without a database engine. These tests do not claim an external-wallet or real-RPC integration result.

The PGlite checks alone do not prove contention across independent PostgreSQL connections. That gap is now covered for the authentication scenarios by `test/postgres.test.ts`: six concurrent real connections, shared limits across two pools, and cleanup waiting for an in-flight verification transaction. The `API checks` workflow runs them against PostgreSQL 18.3 on every push to `main`. Configured external RPC endpoints, external-wallet handoff, iOS integration and a real testnet signature still require acceptance tests.

Native `WalletAuthentication.swift`, `WalletSignInStore.swift` and `WalletHTTPAPI.swift` implement the client message policy, explicit review/sign separation, account/topic/chain generation guards, late-token revocation, separate Keychain storage, and HTTPS auth transport that refuses redirects. They are connected to the Reown WalletKit adapter (`ReownWalletConnector.swift`) and the app's Wallet sign-in screen when the build carries a Reown project ID. Their isolated native tests use doubles; they do not establish an actual wallet session.

## Before exposing a wallet endpoint

Confirm the network, application origin/sign-in URI and Reown metadata. Configure the trusted RPC provider, production database and deployment-level traffic controls, then test external-wallet signing and the unsupported-wallet result. Integrate wallet identity with card ownership explicitly. Use provider secret storage for service credentials; wallet signing remains external and no private-key import is planned.

The iOS app must invalidate its authentication assumptions on account/chain changes and distinguish wallet connection from an authenticated API session. None of those integration steps is represented as complete by this module.
